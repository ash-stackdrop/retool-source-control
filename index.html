Handbook for builders

Source control in Retool

Once an app is protected, every change goes through a branch, a commit and a pull request before it reaches main. This handbook gets you there in three parts. Read them in order the first time, then come back to part 3 when something looks wrong.

The idea

Retool

is where you make changes

On a branch, in the editor you already use.

Git provider

is where changes get approved

Pull request, review, merge.

main

is the source of truth

Retool deploys every merge to main.

Protected means locked on main.

Once an app, workflow, resource, theme or query is protected, its main version can't be edited in Retool. To change it, you create a branch.

A branch covers your whole instance.

On one branch you can edit several apps, modules, workflows and queries. They all go into the same pull request.

Merging happens in your Git provider.

GitHub, GitLab, Bitbucket, Azure Repos or AWS CodeCommit. Never inside Retool.

Deploys are automatic.

Retool watches main and syncs whatever changed. Self-hosted instances check every 10 seconds.

What goes into Git

Goes into Git
  • Apps built with the new app builder
  • Classic apps and modules
  • Workflows
  • Resources (production environment settings)
  • Themes
  • Query Library queries
  • Agents
Stays out of Git
  • Secrets and passwords. Use configuration variables or a secrets manager.
  • Uploaded images. They stay on the instance where they were uploaded, so host them at a URL.
  • Releases, unless multi-instance releases are on.
  • Non-production resource environments.
  • Anything that isn't protected.

How your team branches

Teams use one of two models. Ask which one you're on before your first branch.

Model A · Retool's recommendation

One main, short feature branches

Every instance reads the same protected main. Branches live a week or less. Releases decide what each instance shows.

Good fit

Most teams.

Costs

Testing before users see a change relies on releases or a staging instance.

Model B · Spaces

A develop branch for a Dev Space

A Dev Space is connected to a develop branch and a Prod Space to main. Features merge into develop for testing, then a pull request promotes develop to main.

Good fit

Teams that want a full test environment on one instance.

Costs

More merges and drift. Config variable names must match exactly in both Spaces.

Our take

Start with model A. Move to model B when you need a separate test environment on the same instance and someone owns the develop-to-main promotions.

For admins: connect Git once Builders can skip this

You need a Retool Enterprise plan and admin rights in Retool. On GitHub you need to be able to create an app in the account that owns the repository; for an organization, that means an org owner or a GitHub App manager. These steps use GitHub. Other providers follow the same shape, and their guides are in Sources.

You'll collect five values for Retool
OwnerRepository nameApp IDInstallation IDPrivate key (base64)

Keep a scratch note open and paste each one in as you go.

  1. Create the repository

    Create a new private repository in the account or organization that will own it. Tick the option to add a README when you create it; that gives you the README.md and the main branch Retool needs. This repo will hold everything you protect. Note its owner and name.

  2. Register a GitHub App

    The GitHub App is how Retool signs in to GitHub. Create it under the same account that owns the repository, or Retool won't be able to reach it.

    1. Open the GitHub Apps page:
      • Organization: profile picture › Your organizations › Settings next to the org › Developer settings › GitHub Apps
      • Personal account: profile picture › Settings › Developer settings › GitHub Apps
    2. Click New GitHub App and fill in the form as shown below.
    3. Click Create GitHub App at the bottom of the page.
    Field on GitHubSet it to
    GitHub App nameAnything unique on GitHub, up to 34 characters, like acme-retool-source-control
    Homepage URLAny valid URL, such as your Retool address. GitHub requires it; Retool doesn't use it.
    Callback URLLeave empty
    Expire user authorization tokensUnticked
    Request user authorization (OAuth) during installationUnticked
    Webhook › ActiveUnticked
    Repository permissions › ContentsRead and write
    Repository permissions › Pull requestsRead and write
    All other permissionsNo access. GitHub adds Metadata: Read-only by itself.
    Where can this GitHub App be installed?Only on this account

    GitHub docs Retool docs

  3. Copy the App ID and generate a private key
    1. After you create the app, GitHub opens its settings page. Under About, copy the App ID. It's a number; don't confuse it with the Client ID. The Owned by name on the same page is the owner you'll give Retool.
    2. Scroll down to Private keys and click Generate a private key. A .pem file downloads. GitHub only keeps the public half, so store this file somewhere safe. If you lose it, generate a new one.
    3. Retool wants the key base64-encoded. Run this in a terminal, then open the text file and copy everything in it:
    # macOS
base64 -i ~/Downloads/acme-retool-source-control.2026-10-05.private-key.pem > github-private-key.txt
# Linux
base64 -w 0 ~/Downloads/acme-retool-source-control.2026-10-05.private-key.pem > github-private-key.txt

    Your file name will differ; it starts with your app's name and the date. If you store the key in Kubernetes Secrets, Retool says to encode it twice. GitHub docs

  4. Install the app on your repository
    1. On the app's settings page, click Install App in the left sidebar.
    2. Click Install next to the account or organization that owns the repo.
    3. Choose Only select repositories, pick your Retool repository, and click Install.
    4. Copy the Installation ID. It's the number at the end of the URL you land on:
    # organization
https://github.com/organizations/acme/settings/installations/12345678
# personal account
https://github.com/settings/installations/12345678

    Lost it? Open the installed app again with Configure from your account or organization settings, and the same URL appears. GitHub docs

  5. Connect Retool
    1. In Retool, go to Settings › Source control and choose Set up GitHub.
    2. Fill in the form with the values you collected:
    Field in RetoolWhat to enter
    GitHub ownerThe Owned by name from step 3, your organization or username
    GitHub repositoryThe repository name only, not the full URL
    GitHub branchmain
    App IDFrom step 3
    Installation IDFrom step 4
    App Private KeyThe base64 text from step 3
    GitHub Enterprise URL and API URLOnly for self-hosted GitHub Enterprise Server. Otherwise leave empty.
    1. Click Test connection. If it fails, recheck the owner, repository name and Installation ID first; those cause most failures.
    2. Click Save and deploy.
  6. Protect main in GitHub

    Add a branch protection rule that requires a review before merging.

  7. Move environment-specific values into configuration variables

    Why: when you protect an app or resource, Retool copies it into Git, and that same copy is deployed to every instance or Space that reads from the repo. A staging URL, database host or API key typed straight into a query or resource goes into Git with it, and then lands on production too.

    A configuration variable keeps that value out of the app. The app only stores a name, such as API_BASE_URL, and each instance or Space sets its own value for that name in its settings. You get one app in Git, with the right value on every instance.

    # Before: hardcoded, so this exact URL deploys everywhere
https://staging-api.example.com/orders

# After: Git only holds the name
{{ environment.variables.API_BASE_URL }}/orders
#   dev instance:  https://staging-api.example.com
#   prod instance: https://api.example.com

    Do it before protecting, because anything already committed stays in Git history. In resources, write {{ environment.variables.NAME }}. In apps and workflows, write {{ retoolContext.configVars.NAME }}. Use exactly the same name on every instance and Space, capitals included.

  8. Add a test deployment check Optional

    A CI step that sends the pull request's commit SHA to POST /api/v2/source_control/test_deploy, using a Retool API token with the Source Control Read and Test Deploy scopes. Retool docs

Also worth doing

Keep Source Control settings to a few admins, since they hold your Git credentials. On self-hosted, VERSION_CONTROL_LOCKED makes an instance read-only, which suits a production instance that should only receive deploys.

The change loop

Step 1 happens once per app. Steps 2 to 7 happen for every change. Click through them.

Once per app

Protect the app

You click

In the apps list, open the app's ··· menu and choose Protect app, then follow the prompts to open the pull request it creates. Workflows have Protect workflow in the same place.

In Git

Merge that pull request in GitHub. The app gets its own folder on main, Retool shows Protection complete, and the app gets the Protected badge.

Watch out

Swap hardcoded URLs and other environment-specific values for configuration variables first, so nothing instance-specific ends up in Git.

Every change

Create a branch

You click

On the protected app, Edit, then Create new branch. Retool suggests a name like yourname/patch-1a2b; replace it with one that says what the change is, like feature/order-search. Tick Allow collaborators if teammates need to commit to it too.

In Git

Nothing yet. Retool creates the branch from main, and it appears in GitHub after your first commit.

Watch out

A new browser tab always opens on main. Check the branch name in the bottom-left status bar before you edit.

Every change

Build on your branch

You click

Nothing new. Build the way you normally do. Users keep running main.

In Git

Nothing yet. Your edits reach Git when you commit.

Tip

You can edit other apps, modules, workflows and queries on the same branch. They join the same pull request.

Watch out

Two builders editing the same component on separate branches will conflict. Split work by page, by module, or by queries versus UI.

Every change, often

Commit

You click

Commit in the top right opens Commit to branch. Write a message and press Commit to <your-branch>. Review changes shows the diff first, with a Past commits tab for what's already on the branch.

In Git

Commit and push happen together. The commit is on the remote branch straight away.

Tip

Commit small and often, with messages that say what changed. Small commits are easy to review and easy to cherry-pick.

When the change is ready

Open a pull request

You click

Click the branch name in the bottom-left status bar, then Create pull request. Check the list of dependencies, then Open pull request.

In Git

A normal pull request into main, made of Toolscript files. See Reviewing a pull request.

Watch out

The same panel lists the apps on your branch. Anything marked Not committed isn't in Git yet, so commit it first. If your change relies on a module, resource or query that also changed, keep it on the same branch or merge that one first.

In your Git provider

Review and merge

You click

Nothing in Retool. A reviewer approves and merges in your Git provider.

In Git

Your branch merges into main with your usual merge strategy.

Just before you merge

Check the pull request for Retool-generated commits that undo someone else’s work, and revert them. See Check Retool’s own commits.

Watch out

Never force-push, rebase or reset main. Retool tracks commit history and gets stuck on commits that no longer exist.

Seconds after the merge

Retool deploys

You click

Usually nothing. Admins can confirm it in the Deployment Dashboard under Settings › Source control, or press Deploy latest for a full sync.

In Retool

Retool deploys what changed. If a deploy fails, the app keeps running its last good version.

Watch out

If the app or workflow uses releases, publish one now. See Getting your change live. Then delete the branch; work added after a merge tends to get lost.

In Retool
Step 1 of 7

Keep your branch up to date

Teammates keep merging while you work. Your admin picks one of these two ways to bring their changes into your branch.

Default

Catch-up commits

When you open something that changed on main, Retool copies the change onto your branch as an automatic commit. You don't need to do anything with it.

Beta

Merge main into your branch

Press Merge main into <branch>. If it merges cleanly, press Commit merge. If there are conflicts, fix the marked lines in the editor first; Retool checks the result before it lets you commit.

Resolving a conflict, file by file When you hit one
FileHow to resolve
metadata.jsonKeep the later version number. If both sides changed a setting, keep one valid value.
.positions/*.jsonKeys must stay unique. Same component moved twice: pick one position. Different components in one spot: keep both.
main.rsx, src/*.rsxFor an edited component, keep the correct change. New components can both stay; their order sets where they render.
lib/*Resolve it like any other code conflict.
Watch out

Broken Toolscript can fail deploys for everyone. Resolve inside Retool when you can, because it validates the result. If you resolve in your Git provider instead, merge right away and stop working on that branch in Retool.

Tip

When a conflict turns into a mess, start a fresh branch from main and redo the change. It's usually quicker.

Admin settings: Settings › Beta › Enable branch merging switches to merging and turns catch-up commits off. Disable auto catch up commits under Settings › Source control turns them off without merging, so builders rebase outside Retool. Retool docs

Check Retool’s own commits before you merge

Retool sometimes adds commits to your branch by itself, such as Retool generated schema changes or catch-up commits. They show up under your name. Most are harmless, but now and then one rolls back work that someone already merged, and your pull request quietly undoes it. Check for this last, once your work on the branch is finished and you’re about to merge.

What to look for in the Commits tab
  1. Retool generated schema changes1a2b3c4Autorolled back a teammate’s change
  2. Add search by email5d6e7f8your commit
  3. Retool generated schema changes9a0b1c2Autoharmless
  4. Revert "Retool generated schema changes"3d4e5f6the fix, made right before merging

Example. Commit names and IDs are made up.

How to fix it
  1. Finish all your work on the branch and commit it in Retool. The revert must be the last change on the branch.
  2. Open the pull request’s Commits tab in GitHub and find the auto-generated commits.
  3. Open each one’s diff. If it deletes or rolls back changes that aren’t part of your work, that’s the one. In our experience it’s usually the first auto-generated commit on the branch.
  4. Revert that commit from a local clone of the repo and push. A revert adds a new commit that undoes it, without rewriting history:
git switch feature/order-search
git pull
git revert 1a2b3c4
git push
  1. Check Files changed once more, then merge straight away.
Revert last, and never reset

Revert only when you’re done. If you revert and then carry on working in Retool, you have to reset the branch to pick up the revert, and your next commit makes Retool generate another of these commits, which you’d have to revert again. Finish everything, revert, merge.

Use a revert, not a reset. A revert adds a commit. Dropping the bad commit with a reset or a force-push breaks things, because Retool tracks your branch history and gets stuck when commits disappear.

Getting your change live

A merge updates main. Whether users see it straight away depends on releases.

ItemUsers runAfter you merge
App without a published releaseThe latest version on mainLive once the deploy finishes.
App with a published releaseThe published releasePublish a new release.
WorkflowIts live releasePublish a new release.
Pick one per app

Either main is what users see, or releases choose what's live. Both work. Mixing them on one app is what causes "I merged it but nothing changed." Decide per app and make sure the team knows.

Running different versions on dev, staging and prod Multi-instance releases

By default a release exists only on the instance where you created it, and it isn't stored in Git. Turning on Enable multi-instance releases under Settings › Source control › Edit settings stores releases in Git, so staging can try release 15 while production stays on 14.

New app builder releases become Git tags. Classic apps and workflows are saved as zip files under dist/apps/, which grows the repo with every release. Retool docs

Reviewing a pull request

A Retool pull request is made of Toolscript, a JSX-like format designed for review. Pick a file to see what it holds and whether anyone should edit it by hand.

apps/order-search/
lib/
src/
.positions/

main.rsx

Hand-edit only to fix a merge conflict

The app's entry point: every component with its id and properties. Nesting shows which component sits inside which.

Simplified example 
<Container id="filtersContainer">
  <Header>
    <Text id="filtersTitle" value="Find an order" />
  </Header>
  <View>
    <TextInput id="searchInput" placeholder="Name or email" />
    <Button id="searchButton" text="Search" />
  </View>
</Container>

<Table id="ordersTable" data="{{ formatRows.data }}" />

The ids are the names you see in the editor. Renaming a component touches every file that refers to it.

functions.rsx

Hand-edit only to fix a merge conflict

Queries and functions available to the whole app. Each query is declared here and points at its body in lib/.

Simplified example 
<SqlQueryUnified
  id="getOrders"
  query={include("./lib/getOrders.sql", "string")}
  resourceDisplayName="orders_db"
/>

metadata.json

Hand-edit only to fix a merge conflict

Version information and app settings. If both sides bumped the version, keep the later number.

.defaults.json

Leave it alone

Generated by Retool. You won't need to open it in review, and hand edits get overwritten.

lib/getOrders.sql

Safe to edit by hand

The body of a SQL query as a plain file. This is where to start reading a review, since query changes carry the most risk.

select id, customer_name, email, status
from orders
where email ilike {{ '%' + searchInput.value + '%' }}
order by created_at desc;

If you change a branch outside Retool, reset the branch from the branch menu so Retool picks it up.

lib/formatRows.js

Safe to edit by hand

The body of a JavaScript query. Same rules as the SQL files.

const rows = formatDataAsArray(getOrders.data);
return rows.map((row) => ({ ...row, status: row.status.toUpperCase() }));

src/page1.rsx

Hand-edit only to fix a merge conflict

In a multipage app, each page gets a file here with its components and the queries that belong to that page. Large containers can also be split out into this folder.

From a real pull request, trimmed 
<SqlQueryUnified
  id="query1"
  query={include("../lib/query1.sql", "string")}
  resourceDisplayName="retool_db"
  resourceName="…"
  warningCodes={[]}
/>
<Frame id="$main" enableFullBleed={false}>
  … the page's components …
</Frame>

.positions/.page1.positions.json

Hand-edit only to fix a merge conflict

Where each component sits on the canvas, per page, with separate files for mobile. Kept apart from logic, so a big diff here usually just means someone moved things around.

From a real pull request 
{
  "table1": { "row": 2.4, "col": 2, "height": 8, "width": 8 }
}
safe to edit conflicts only leave alone
Review order

Read lib/ first, then the .rsx files for changed properties and renamed ids, then skim .positions. Finally, switch to the branch in Retool and click through the change yourself.

Glossary

Protected
Under source control. The main version is locked in the editor, and changes go through branches.
Branch owner
The person who created a branch. Only they can delete or rebase it.
Collaborative branch
A branch created with Allow collaborators ticked, so anyone in the organization can commit to it. Only admins can rename, reset or delete it.
Catch-up commit
An automatic commit that copies changes from main onto your branch.
Toolscript
Retool's JSX-like file format for protected items. Files end in .rsx.
Deployment Dashboard
The admin view of recent deploys, with status, commit, duration and logs.
Deploy latest
A full deploy that syncs everything from main, started by an admin. Normal deploys sync only what changed.
Release
A published version of an app or workflow that users run. Stored per instance by default.
Multi-instance release
A release stored in Git, so different instances can run different versions.
Space
An isolated area inside one Retool instance, with its own apps, resources and Source Control settings.
Configuration variable
A named value that can differ per Space or instance, used instead of hardcoded URLs and keys.
Read-only instance
A self-hosted instance with VERSION_CONTROL_LOCKED set. It only receives deploys.
